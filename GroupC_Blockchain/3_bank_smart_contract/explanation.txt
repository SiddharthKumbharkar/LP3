ASSIGNMENT 3 - BANK ACCOUNT SMART CONTRACT
==========================================

Problem Statement
-----------------

Write a smart contract on a test network, for Bank account of a customer for following operations: Deposit money, Withdraw Money, Show balance.

Explanation
-----------

Bank.sol implements a simple per-account bank with deposit, withdraw,
and getBalance, using a mapping(address => uint256) so every wallet
has its own independent balance tracked in wei.

- mapping(address => uint256) balances — a key-value store built into Solidity, here mapping each wallet address to its own balance. Every address automatically "has" an entry (defaulting to 0) without needing to be explicitly initialized.
- deposit() public payable — payable allows the function to receive Ether. msg.value is the amount of Ether (in wei) sent with the call; it's added to balances[msg.sender], where msg.sender is whoever called the function. A require guards against zero-value deposits.
- withdraw(uint256 amount) public — checks the caller has sufficient balance, deducts it from storage first, then sends Ether back using a low-level msg.sender.call{value: amount}(""), checking the returned success flag. Deducting the balance before the external transfer (checks-effects-interactions pattern) guards against re-entrancy attacks.
- getBalance() public view — a view function; it only reads state and doesn't modify it, so calling it directly from outside costs no gas. It returns the balance of whoever calls it (msg.sender), not an arbitrary address.
- No events are emitted here (unlike some bank contract variants) — the focus of this version is the minimal deposit/withdraw/balance flow.

How to deploy and run on Remix with Sepolia + MetaMask
-------------------------------------------------------------

0. One-time MetaMask setup (skip if already done):
   - Install the MetaMask browser extension and create/import a wallet.
   - In MetaMask, open the network dropdown (top left) and enable
     "Show test networks" in Settings > Advanced if Sepolia isn't
     listed, then select "Sepolia" as the active network.
   - Get free test ETH: copy your wallet address from MetaMask, visit
     a Sepolia faucet (e.g. sepoliafaucet.com or the Alchemy/Infura
     Sepolia faucet), paste your address, and request test ETH. Wait
     for it to arrive (check the balance in MetaMask).
1. Open Remix IDE (https://remix.ethereum.org) in the browser.
2. In the File Explorer (left sidebar), create a new file named Bank.sol
   under contracts/, and paste in the exact code from
   GroupC_Blockchain/3_bank_smart_contract/Bank.sol.
3. Go to the "Solidity Compiler" tab (left sidebar). Set the compiler
   version to match the pragma in the file: 0.8.38 (or let Remix
   auto-select a compatible 0.8.x version). Click "Compile Bank.sol".
   A green checkmark confirms a clean compile.
4. Go to the "Deploy & Run Transactions" tab.
   - Environment: click the dropdown (shows "Remix VM" by default) and
     select "Browser Extension" (this is the current Remix UI's name
     for what older versions/guides call "Injected Provider -
     MetaMask" — same thing). MetaMask will pop up asking to connect —
     approve it. Confirm the network shown next to the Environment
     dropdown says "Sepolia" — if it shows a different network, switch
     networks inside MetaMask itself, not in Remix.
   - Account: the dropdown should now show your MetaMask address and
     its Sepolia ETH balance (e.g. "0x1234...5678 (0.49961 ETH)").
   - Contract: make sure "Bank" is selected in the dropdown next to
     the Deploy button.
   - Click "Deploy" — MetaMask will pop up a transaction confirmation
     showing the estimated gas fee; click "Confirm". Wait a few
     seconds for the transaction to be mined on Sepolia.
5. Once deployed, the contract appears under "Deployed Contracts" with
   three buttons: deposit, withdraw, getBalance.
   - deposit: the "Value" field only accepts whole numbers, not
     decimals, even when the unit is set to Ether — so keep the unit
     dropdown on "wei" and type the equivalent whole number instead,
     e.g. 1000000000000000 for 0.001 ether (Ether amount x 10^18 =
     wei). Then click the deposit button — the value field is what
     gets sent as msg.value. Keep amounts small since this is real
     (though worthless) Sepolia ETH from a faucet, and you'll want
     enough left for several calls.
   - withdraw: enter an amount in wei in the withdraw input box
     (e.g. 500000000000000 for 0.0005 ether) and click withdraw.
   - getBalance: click it directly (blue button = view/free call) to
     read your current balance in wei.
6. To test with a different account, switch the active account inside
   MetaMask itself (or add a second account there), then reselect it
   in Remix's "Account" dropdown and call deposit/withdraw/getBalance
   again — notice each account has its own independent balance.

What to observe
---------------

- Each state-changing call (deposit, withdraw) pops up a MetaMask
  confirmation showing the estimated gas fee in Sepolia ETH; after
  confirming, the Remix terminal/console log at the bottom shows the
  transaction hash, gas used, and actual transaction fee.
- Click the transaction hash link (or copy it) and paste it into
  https://sepolia.etherscan.io to see the real, permanent transaction
  record on the Sepolia block explorer — including gas used, gas
  price, and total fee paid.
- getBalance is a view function (shown as a blue button in Remix,
  versus orange/red for state-changing functions), so calling it
  directly costs no gas and needs no MetaMask confirmation.
- Try withdrawing more than your balance — the require check should
  cause the transaction to revert, and Remix will show the error
  message "Insufficient balance" in the console.
- Compare the gas used by deposit vs. withdraw: withdraw does more
  work (a balance check, a storage write, AND an external call to
  send Ether back), so it typically costs more gas than deposit.

Viva Questions & Answers
------------------------

Q1. What is a smart contract?
Self-executing code deployed on a blockchain that runs exactly as written, without a central authority — once deployed, its logic is immutable and its execution is enforced by the blockchain network's consensus rules.

Q2. What is msg.sender and msg.value?
msg.sender is the address that called the current function (the caller's wallet). msg.value is the amount of Ether (in wei) sent along with the function call — only meaningful for payable functions.

Q3. Why is deposit() marked payable but getBalance() is not?
payable allows a function to receive Ether as part of the call. deposit needs to accept Ether, so it must be payable. getBalance only reads data and never needs to receive funds, so it isn't (and shouldn't be) payable.

Q4. What is gas, and why does every state-changing transaction cost it?
Gas is the unit measuring computational work on Ethereum. Every operation (storage write, computation, etc.) consumes gas, and the caller pays gas used x gas price as the transaction fee — this prevents infinite loops/spam by making computation costly, and compensates miners/validators for processing the transaction.

Q5. Why does getBalance() not cost gas when called directly?
It's declared view, meaning it only reads blockchain state without modifying it. Calls that don't change state can be answered locally by a node without needing network-wide consensus/execution, so they're free when called directly (not as part of a state-changing transaction).

Q6. What is re-entrancy, and how does this contract protect against it?
Re-entrancy is an attack where a malicious contract calls back into withdraw before the first call finishes, potentially draining funds by repeatedly withdrawing before the balance is updated. This contract updates balances[msg.sender] before sending Ether out (checks-effects-interactions pattern), so even if the receiving contract tries to re-enter, the balance is already deducted.

Q7. What does the require statement do, and what happens if its condition fails?
It checks a condition and, if false, immediately reverts the entire transaction (undoing all state changes made so far in that call) and returns the remaining gas, along with the provided error message.

Q8. Why use msg.sender.call{value: amount}("") instead of transfer() or send()?
transfer() and send() forward a fixed, small gas stipend (2300 gas), which can fail against contracts with more complex fallback logic and is no longer considered best practice. call forwards all remaining gas and returns a success boolean that must be explicitly checked (as this contract does with require(success, ...)), giving more flexibility and control.

Q9. Why use a mapping instead of an array to store balances?
A mapping gives O(1) direct lookup by address with no iteration needed, and doesn't require tracking which addresses exist — perfectly suited for "lookup balance by owner" access patterns, unlike an array which would need to be searched.

Q10. What would happen if two withdraw transactions from the same account were sent at nearly the same time?
Ethereum processes transactions sequentially (one block at a time, transactions ordered within a block) — so they aren't truly concurrent. Whichever is processed first will update the balance, and the second transaction's require check will then see the already-reduced balance, failing if there's insufficient funds for the second withdrawal.
