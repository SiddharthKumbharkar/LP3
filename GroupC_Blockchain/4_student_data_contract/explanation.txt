ASSIGNMENT 4 - STUDENT DATA SMART CONTRACT
==========================================

Problem Statement
-----------------

Write a program in solidity to create Student data. Use the following constructs: Structures, Arrays. Deploy this as a smart contract on Ethereum and observe the transaction fee and Gas values.

Explanation
-----------

StudentData.sol stores student records on-chain using:
- a struct Student { rollNo, name, marks }
- a dynamic array Student[] students holding all records
- a receive() and fallback() function, to demonstrate what happens
  when the contract receives plain Ether with no matching function call

- struct Student — a custom composite type bundling related fields (rollNo, name, marks) together, similar to a class/record in other languages — lets one student be represented and passed around as a single unit.
- Student[] students — a dynamic array (grows as needed) stored permanently in contract storage; every element costs gas to write since it persists on-chain.
- addStudent(rollNo, name, marks) public — creates a new Student and pushes it onto the array; this is a state-changing (storage write) operation and costs gas. The roll number is supplied by the caller rather than auto-generated.
- getStudent(uint256 index) public view — returns a student's (rollNo, name, marks) as a tuple by reading students[index]; reverts automatically if index is out of range (Solidity's built-in array bounds check).
- getCount() public view — a simple view helper returning students.length.
- receive() external payable — a special function that runs automatically whenever the contract receives Ether with no data attached (e.g. a plain transfer sent directly to the contract's address, not through a specific function call).
- fallback() external payable — a special function that runs automatically when a call is made to this contract that doesn't match any existing function signature (e.g. calling a typo'd function name, or sending data that doesn't decode to a known function).
- Both receive() and fallback() emit a Received event here, so you can see in the logs which one fired and with what amount.

How to deploy and run on Remix with Sepolia + MetaMask
-------------------------------------------------------------

0. One-time MetaMask setup (skip if already done):
   - Install the MetaMask browser extension and create/import a wallet.
   - In MetaMask, open the network dropdown (top left) and enable
     "Show test networks" in Settings > Advanced if Sepolia isn't
     listed, then select "Sepolia" as the active network.
   - Get free test ETH: copy your wallet address from MetaMask, visit
     a Sepolia faucet (e.g. sepoliafaucet.com or the Alchemy/Infura
     Sepolia faucet), paste your address, and request test ETH. Wait
     for it to arrive (check the balance in MetaMask).
1. Open Remix IDE (https://remix.ethereum.org) in the browser.
2. In the File Explorer (left sidebar), create a new file named
   StudentData.sol under contracts/, and paste in the exact code
   from GroupC_Blockchain/4_student_data_contract/StudentData.sol.
3. Go to the "Solidity Compiler" tab. Set the compiler version to
   0.8.38 (matching the pragma) or let Remix auto-select a compatible
   version. Click "Compile StudentData.sol" and confirm the green
   checkmark.
4. Go to the "Deploy & Run Transactions" tab.
   - Environment: click the dropdown (shows "Remix VM" by default) and
     select "Browser Extension" (this is the current Remix UI's name
     for what older versions/guides call "Injected Provider -
     MetaMask" — same thing). MetaMask will pop up asking to connect —
     approve it. Confirm the network shown next to the Environment
     dropdown says "Sepolia" — if it shows a different network, switch
     networks inside MetaMask itself, not in Remix.
   - Account: the dropdown should now show your MetaMask address and
     its Sepolia ETH balance.
   - Contract: make sure "StudentData" is selected in the dropdown.
   - Click "Deploy" — MetaMask will pop up a transaction confirmation
     showing the estimated gas fee; click "Confirm". Wait a few
     seconds for the transaction to be mined on Sepolia.
5. Once deployed, under "Deployed Contracts" you'll see addStudent,
   getStudent, getCount, and the contract's address.
   - addStudent: fill in rollNo (e.g. 1), name (e.g. "Alice"), and
     marks (e.g. 85), then click addStudent. Repeat with different
     values (rollNo 2, "Bob", 90) to add a few more records — each
     call is a transaction that costs gas because it writes to
     storage (students.push(...)).
   - getStudent: enter an index (e.g. 0) and click it (blue button =
     free, view call) to read back (rollNo, name, marks) for that
     student.
   - getCount: click it directly to see how many students have been
     added so far.
6. To trigger receive()/fallback(): in the "Deploy & Run Transactions"
   tab, find the deployed contract's address, copy it, then use the
   "Low level interaction" section at the bottom of the deployed
   contract card — the Value field there only accepts whole numbers,
   not decimals, even on Ether, so keep the unit on "wei" and type a
   small whole number instead, e.g. 1000000000000000 for 0.001 ether
   (to keep the real Sepolia ETH spend small). Leave CALLDATA empty,
   and click the "Transact" button next to the low-level interaction
   box. MetaMask will pop up to confirm this transfer. Since there's
   no matching function and no data, this triggers receive(). Check
   the logs in the Remix terminal (or the transaction on Sepolia
   Etherscan) to see the Received event fire with how = "receive".

What to observe
---------------

- Each state-changing call (addStudent, or the low-level transfer
  that triggers receive) pops up a MetaMask confirmation showing the
  estimated gas fee in Sepolia ETH; after confirming, the Remix
  console shows the transaction hash, gas used, and actual fee paid.
- Paste the transaction hash into https://sepolia.etherscan.io to see
  the real, permanent record on the Sepolia block explorer, including
  the emitted event logs.
- Compare the gas cost of addStudent (storage write) against the
  zero-cost reads from getStudent / getCount (storage read only, no
  state change, no MetaMask confirmation needed).
- Adding a string field (name) is more expensive than fixed-size
  fields (uint256), since dynamic types take extra storage slots -
  note this in the gas values reported by Remix.
- Try calling getStudent with an index that doesn't exist (e.g. 99
  when only 2 students were added) — Solidity's automatic array
  bounds check causes the transaction to revert.
- Send plain Ether (no data) directly to the contract address and
  confirm the Received event shows how = "receive"; this is the
  pattern real wallets and contracts use to accept simple transfers.

Viva Questions & Answers
------------------------

Q1. What is a struct in Solidity, and why use one here instead of separate arrays for rollNo, name, marks?
A struct groups related fields into a single custom type, so one Student holds all of a student's data together. Using parallel separate arrays (one for roll numbers, one for names, etc.) would be error-prone — you'd have to keep every array in sync manually, whereas a struct array keeps each student's data atomically bundled.

Q2. What's the difference between a dynamic array and a fixed-size array in Solidity?
A dynamic array (like Student[] students) can grow or shrink at runtime via push/pop. A fixed-size array (e.g. uint256[10]) has its length baked in at compile time and cannot change. Dynamic arrays are needed here since the number of students isn't known in advance.

Q3. Why does addStudent cost gas but getStudent doesn't (when called directly)?
addStudent writes new data to contract storage (students.push(...)), which permanently changes the blockchain's state and must be processed via a mined/validated transaction — this costs gas. getStudent is a view function; it only reads existing storage without changing it, so it can be answered locally by a node for free.

Q4. What is the difference between memory and storage in Solidity?
storage refers to persistent, on-chain data (expensive to read/write, lives forever on the blockchain). memory is temporary data that exists only during a function's execution (cheaper, discarded afterward) — getStudent copies a storage struct into a memory variable (Student memory s) so it can return the values without creating a persistent reference.

Q5. What is the difference between receive() and fallback(), and when does each run?
receive() runs when the contract is sent plain Ether with no calldata (no function being called, just a transfer). fallback() runs when a call is made with either calldata that doesn't match any function signature, or when there's no receive() defined and Ether is sent with data. Both must be marked external, and both typically need payable if the contract should be able to accept Ether through them.

Q6. Why would a contract need a receive() or fallback() function at all?
Without them, sending Ether directly to the contract's address (not via a specific payable function) would simply fail and revert — these special functions let a contract gracefully accept such transfers (and, as shown here, log them) instead of rejecting them outright.

Q7. Why does getStudent revert automatically for an out-of-range index, without an explicit require check in this version?
Solidity performs automatic bounds checking on array access (students[index]) — if index is outside the array's current length, the EVM throws a panic/revert on its own, so no manual require statement is strictly needed here (though adding one can give a clearer custom error message).

Q8. Why is storing a string field more expensive than a uint256 field?
string is a dynamically-sized type — Solidity has to handle it in variable-length storage slots (potentially using multiple 32-byte slots depending on length), while uint256 always fits in exactly one fixed 32-byte slot — the extra bookkeeping and potential extra slots for dynamic types makes them costlier to store.

Q9. What is the purpose of the Received event, and why log both receive() and fallback() through it?
Events let off-chain applications (and the Remix console, for testing) observe what happened on-chain without expensive storage reads. Logging both paths through the same event with a "how" field makes it easy to tell, after the fact, which special function actually handled an incoming transfer.

Q10. What's the difference between "gas used" and "transaction fee"?
Gas used is the amount of computational work consumed (measured in gas units). Transaction fee is the actual cost paid: gas used x gas price (gas price being how much the sender is willing to pay per unit of gas, in gwei) — the same operation can have the same gas used but a different fee depending on current network gas prices.
